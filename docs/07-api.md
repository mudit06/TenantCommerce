# 07 API

## Three API surfaces

| Surface | Base | Who | Built by |
|---|---|---|---|
| Payload REST + GraphQL | `/api/<collection>`, `/api/graphql` | Admin UI, staff tools, scripts | Auto-generated by Payload from collections; protected by access control |
| Payload Local API | in-process `payload.find(...)` | Server Components, services, jobs | Payload. Fastest; used for all storefront reads via `src/lib/data` |
| Storefront API | `/api/store/v1/*` | The PWA in the browser (cart, checkout, account, search) | Our Payload custom endpoints in `src/modules/*/endpoints` |
| Webhooks in | `/api/webhooks/<provider>/:tenantId` | Razorpay, Shiprocket (as `courier`), WhatsApp, MSG91, Resend (email events) | Our endpoints |

Rules for the storefront API:

- Tenant comes from the `Host` header only (`resolveTenantFromRequest`). Never from the body.
- JSON only. Request bodies validated with zod schemas from `src/lib/validation`.
- Response envelope: `{ data, error: null }` or `{ data: null, error: { code, message, fields? } }`.
  HTTP status codes are meaningful (400 validation, 401, 403, 404, 409 conflict, 422 business rule,
  429 rate limit).
- Money always as `{ amountMinor, currency }`; dates ISO 8601 UTC.
- Pagination: `?page=1&limit=24` (max 100), response `meta { page, limit, total, totalPages }`.
- Versioned under `/v1`. Breaking changes go to `/v2`.
- Mutations accept an `Idempotency-Key` header (required on `checkout` and `payments`).
- Rate limits noted below are per IP + per tenant, defaults overridable.

Server Components do not call these endpoints over HTTP; they call the same service functions
directly. The endpoints exist for client-side interactions and future native apps.

### Cart
Cart identified by `cart_id` HTTP-only cookie (anonymous) or the logged-in customer. Merged on login.
| Method | Path | Purpose |
|---|---|---|
| GET | `/cart` | Current cart with server-computed totals |
| POST | `/cart/items` | `{ variantId, qty }` add |
| PATCH | `/cart/items/:itemId` | `{ qty }` |
| DELETE | `/cart/items/:itemId` | Remove |
| POST | `/cart/coupon` | `{ code }` apply; the answer says why a code doesn't work ("Add ₹600 more to use DIWALI10") without revealing other codes. Rate limit 10/10 min per cart and IP (stops code guessing) |
| DELETE | `/cart/coupon` | Remove coupon |
| GET | `/cart/coupons` | Public coupons, each marked usable or not for this cart, with the reason |
| POST | `/cart/contact` | `{ email?, phone?, offersOptIn: { email, whatsapp } }` saved from the checkout contact step, so an abandoned cart can be reminded; only with offer consent |
| GET | `/cart/restore/:token` | Restores the cart from a reminder link on any device (single cart, token valid 7 days), then redirects to `/cart` |
| POST | `/cart/estimate` | `{ pincode }` shipping + tax estimate |

Every cart response carries `appliedOffers[]` (scheme and coupon, with the amount each takes off)
and `lines[].discountMinor`, all worked out by the server (docs/11).

### Checkout and payment
| Method | Path | Purpose |
|---|---|---|
| POST | `/checkout` | `{ contact, shippingAddress, billingAddress?, buyerGstin?, paymentMethod, whatsappOptIn, offersOptIn? }`. Validates stock, serviceability, COD rules, the coupon and scheme limits, recomputes totals and discounts, reserves stock, holds the coupon use, attaches the referral (cookie or affiliate coupon, never the affiliate's own order), creates order (`pending`), records the WhatsApp and offer choices in `contact-preferences`, sets the signed `order_access` cookie for this order (docs/05). For Razorpay returns `{ orderId, provider: 'razorpay', providerOrderId, keyId, amountMinor }`; for COD confirms immediately. Idempotency-Key required. Rate limit 10/min |
| GET | `/orders/:orderNumber` | Guest order detail and invoice link; needs the `order_access` cookie for that order or a signed-in owner, otherwise 404 |
| POST | `/guest-orders/otp/send` | `{ orderNumber, email }` sends a 6-digit code to the order's email if they match (same response either way; rate limit 3/10 min) |
| POST | `/guest-orders/otp/verify` | `{ orderNumber, email, code }` -> 30-minute `order_access` cookie for that order |
| POST | `/payments/razorpay/verify` | `{ orderId, razorpay_payment_id, razorpay_order_id, razorpay_signature }` client-side confirmation; webhook remains source of truth |
| GET | `/track/:code` | Parcel journey for the `https://<store>/t/<code>` link in every message and email: statuses, courier, tracking number; no address or contact details. No login. Rate limit 30/min |
| PATCH | `/track/:code/preferences` | `{ whatsapp?: false, sms?: false }` stop updates for that order's phone (docs/18) |

## Webhooks in (`/api/webhooks`)

| Path | Events | Handling |
|---|---|---|
| `/razorpay/:tenantId` | `payment.captured`, `payment.failed`, `order.paid`, `refund.processed`, `refund.failed` | Verify `X-Razorpay-Signature` with tenant secret; dedupe on event id; enqueue job; respond 200 fast |
| `/courier/:tenantId` | Shiprocket tracking updates (MVP). Shiprocket refuses URLs containing "shiprocket", "sr" or "kr" | Check the `x-api-key` token; always answer 200; dedupe on AWB + status + scan time; re-read tracking by AWB, then move the parcel journey (docs/11), which messages the shopper |
| `/whatsapp/:tenantId` | Message statuses (order updates and offer messages), shopper replies, the "Stop offers" quick reply, template approvals (vendor's own Meta app, MVP) | GET handshake with the verify token; verify `X-Hub-Signature-256` with the tenant's app secret; dedupe; enqueue |
| `/whatsapp` | The same, for vendors connected through the platform's Meta app (Phase 2) | Signature with `META_APP_SECRET`; tenant from `phone_number_id` |
| `/msg91/:tenantId` | SMS delivery reports (MVP) | Per-tenant `?token=`; match on our reference |
| `/resend` | Email delivered, bounced, complained (marked as spam), clicked (MVP) | Svix signature with `RESEND_WEBHOOK_SECRET`; tenant from the message tags we set when sending; a complaint or hard bounce stops offer emails to that address |

All `/api/admin/v1/*` endpoints check the `Origin` header against the host (cookie sessions) and
run their writes in one database transaction (`src/lib/db/transaction.ts`). Commands inside a
Mongo transaction must run one after another, never in `Promise.all`.

## Outbound webhooks and public vendor API (Later)

Per-tenant API keys with scopes (`catalog:read`, `orders:read`, `inventory:write`) for ERP/Tally
sync; outbound webhooks `order.created`, `order.paid`, `order.shipped`, `inventory.low` signed with
HMAC and retried with backoff.
